## Description

NestJS user service with MySQL migrations and `user_profiles` storage. Configure
the database connection in `.env` using `.env.example` as a template.

Run these database commands independently from this project directory:

```bash
npm run migration:run
npm run seed
```

`npm run migration:run` creates the `user_profiles` table and records the
migration in TypeORM's `migrations` table. `npm run seed` inserts a profile
using `SEED_PROFILE_USER_ID` and `SEED_PROFILE_NAME` from `.env`. Set the user
ID to an existing UUID from auth-service. The seed skips a profile if one
already exists for that user. The profile stores the auth user ID but does not
create a cross-service database foreign key.

## API

Fetch the authenticated user's profile. Send the auth-service access token in
the `Authorization` header; the `sub` claim identifies the `userId` to look up.
Configure `JWT_SECRET` in `.env` to exactly match auth-service's secret.

```http
GET /api/v1/profile
Authorization: Bearer <accessToken>
```

The token signature and expiration are verified using HS256 before querying the
database. Missing, invalid, expired, or malformed-subject tokens return
`401 Unauthorized`. The response contains the user's ID, name, and timestamps;
users without a profile receive `404 Not Found`. The profile table does not
create a cross-service database foreign key.

User-service also consumes the Kafka topic `user.registered.v1`. It validates
each event and upserts the user's ID and name into `user_profiles`; processing
is safe to retry. The consumer replays retained events on its first start so
registrations published before the consumer starts are not skipped. Start
Kafka and create the topic before user-service; `KAFKA_BROKERS` defaults to
`localhost:9092`.
The event payload is `{ "eventId": "...", "eventType": "user.registered.v1",
"occurredAt": "...", "data": { "userId": "...", "name": "..." } }`.

Application and HTTP request logs are written under
`logs/YYYY-MM-DD/info.log` and `logs/YYYY-MM-DD/error.log` in this service
directory, using UTC date folders. Errors and fatal logs go to `error.log`;
all other levels go to `info.log`. Each line is formatted as
`YYYY-MM-DD HH:mm:ss Utc : content`, with the log details encoded as JSON.
HTTP log entries include the route, method, status code, and duration; request
bodies and query strings are not logged. In Docker, the `logs/` folder is
bind-mounted so files persist on the host.

## Deployment

When you're ready to deploy your NestJS application to production, there are some key steps you can take to ensure it runs as efficiently as possible. Check out the [deployment documentation](https://docs.nestjs.com/deployment) for more information.

If you are looking for a cloud-based platform to deploy your NestJS application, check out [Mau](https://mau.nestjs.com), our official platform for deploying NestJS applications on AWS. Mau makes deployment straightforward and fast, requiring just a few simple steps:

```bash
$ yarn install -g @nestjs/mau
$ mau deploy
```

With Mau, you can deploy your application in just a few clicks, allowing you to focus on building features rather than managing infrastructure.

## Observability

In production applications, observability is essential for understanding how your system behaves, detecting issues early, and maintaining reliable performance.

[NestJS Observe](https://observe.nestjs.com) automatically instruments your NestJS application, giving you deep visibility into your system with minimal setup:

- **Distributed tracing:** Follow requests across services and understand how they flow through your system.
- **Waterfall analysis:** Visualize request execution and identify slow operations, bottlenecks, and unexpected delays.
- **Performance analysis:** Analyze application performance in real time and quickly pinpoint areas that need optimization.
- **Metrics:** Track key application and infrastructure metrics to understand system health and performance trends.
- **Logging:** Centralize and correlate logs with traces and other telemetry to make debugging easier.
- **Error tracking:** Detect errors quickly and investigate their root causes with the surrounding context.
- **SLA monitoring:** Track service-level objectives and identify when your application is approaching or exceeding defined thresholds.
- **Alarms and alerts:** Set up alerts for critical errors, performance degradation, SLA violations, and other anomalies so your team can react quickly.

To add it to this project:

```bash
$ yarn install @nestjs/observe
```

Then follow the [setup guide](https://docs.nestjs.com/observability/overview) - it takes a single import and an app key.

The free plan needs no payment details and covers 300,000 events a month. You can also browse the [live demo](https://www.observe-demo.nestjs.com/dashboard) first - the whole dashboard over a busy service's data, with nothing to install.
